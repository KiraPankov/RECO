# Методика и результаты тестирования

## Что проверяется

1. **Тестовые диалоги** — распознавание, диаризация, временные метки, работа LLM (`tools/eval/final_eval.py`).
2. **Контрольные наборы open_stt** с ручной разметкой — распознавание на настоящей речи и пунктуация LLM (`tools/eval/openstt_eval.py`).
3. **Код приложения** — юнит-тесты и компиляция.

Оба теста качества запускает сценарий GitHub Actions `.github/workflows/eval.yml`: *Actions → Тесты качества → Run workflow*. Он берёт ровно те файлы моделей, что попадают в APK. Конвейер на Python повторяет приложение:
- sherpa-onnx 2.0.1 и LiteRT-LM 0.19.1;
- те же параметры диаризации и нарезки;
- тот же промпт, шаблон чата и проверка слов LLM.

Результаты появляются в сводке запуска и в артефакте `eval-results`.

## Метрики

- **WER** — пословная ошибка: нижний регистр, без пунктуации, ё → е.
- **WER без фраз с цифрами.** В open_stt числа записаны словами, а Parakeet пишет цифрами, поэтому такие фразы считаются отдельно.
- **Точность диаризации** — доля времени речи эталона, отнесённого к правильному говорящему (при оптимальном сопоставлении меток).
- **Ошибка начала / конца** — средний модуль отклонения границ реплик от эталона, мс.
- **LLM: исправлено / без изменений / отклонено** — в скольких фрагментах LLM изменила пунктуацию, вернула текст как был, и сколько её ответов отброшено проверкой слов.
- **RTF** — время обработки / длительность записи.

## Результаты: с LLM (GitHub Actions)

Прогон «Тесты качества» в GitHub Actions ([запуск](https://github.com/KiraPankov/RECO/actions/runs/42411744966)): те же модели, что в APK, LLM включена, 4 ядра CPU.

**Тестовые диалоги**

| Запись | WER | Диаризация | Говорящих | Ошибка начала / конца | LLM: исправлено / без изменений / отклонено | RTF |
|---|---|---|---|---|---|---|
| clean | 1,7% | 99,0% | 4 | 23 / 68 мс | 0 / 1 / 7 | 0,69 |
| quiet_dc | 0,9% | 98,9% | 4 | 25 / 70 мс | 0 / 0 / 8 | 0,48 |
| noisy_snr5 | 12,1% | 99,0% | 4 | 105 / 211 мс | 1 / 1 / 6 | 0,92 |

WER на clean и noisy_snr5 немного выше, чем в прогоне на ПК выше. Причина — не LLM: проверка слов не пропускает изменений слов, а WER на open_stt до и после LLM совпадает в точности. Распознавание и кластеризация на другом процессоре и с другим числом потоков дают немного другой результат. RTF выше из-за LLM.

**Контрольные наборы open_stt** (по 300 фраз из каждого набора, ручная разметка)

| Набор | Фраз | WER распознавания | WER после LLM | WER без фраз с цифрами | Пунктуация до / после LLM | LLM: исправлено / без изменений / отклонено | RTF распознавания / LLM |
|---|---|---|---|---|---|---|---|
| asr_calls_2_val (телефон) | 300 | 33,2% | 33,2% | 33,0% | 97,9% / 97,9% | 14 / 17 / 253 | 0,10 / 0,82 |
| public_youtube700_val | 300 | 23,3% | 23,3% | 23,1% | 90,4% / 90,4% | 6 / 9 / 278 | 0,10 / 0,86 |
| buriy_audiobooks_2_val | 300 | 20,8% | 20,8% | 20,8% | 92,3% / 92,3% | 11 / 19 / 256 | 0,09 / 0,73 |

**Выводы по LLM:**
- WER после LLM совпадает с WER распознавания на всех наборах — проверка слов работает, LLM не может ухудшить распознавание.
- Qwen3-0.6B в большинстве случаев (84–93% фрагментов) пытается изменить слова, и такие ответы отбрасываются. Принимаются 2–5% ответов. Доля фраз с пунктуацией при этом не меняется: Parakeet уже ставит пунктуацию сам.
- LLM — самый медленный этап: RTF ≈ 0,8 против ≈ 0,1 у распознавания.
- WER на open_stt заметно выше, чем на тестовых диалогах: это настоящая речь — телефонная связь, шум, разговорная лексика, — а разметка open_stt местами отличается по нормализации (дефисы, сокращения).

WER после LLM обязан совпадать с WER распознавания: если он отличается, сценарий завершается с ошибкой.

## Сравнительные замеры (обоснование решений)

**Разрез по паузам Silero VAD** (noisy_snr5). Раньше pyannote склеивал на шуме конец первой реплики, ответ второго участника и следующую реплику первого в один сегмент. Реплика «Хорошо. Какие сроки на исправление» доставалась второму участнику, а короткое «Согласен» — лишнему пятому.

| Вариант | WER | Диаризация | Говорящих | Ошибка начала / конца | Реплик |
|---|---|---|---|---|---|
| Без разреза (прежняя версия) | 12,1% | 88,5% | 5 | 1272 / 1190 мс | 6 |
| **Разрез по паузам + отпечаток для кусков ≥ 0,5 с** (выбрано) | **10,3%** | **99,0%** | **4** | **105 / 211 мс** | **8** |

Порог VAD: при 0,5 на шуме паузы между репликами не находятся, при 0,6–0,8 результат одинаковый (99,0%), выбран 0,7. На clean и quiet_dc результат не изменился. На том же диалоге с шумом в 0,5 и 1,4–2 раза от исходного: диаризация 97,4% → 98,8% (лишний говорящий пропал) и без изменений соответственно.

**Модель «отпечатка голоса» для диаризации** (pyannote + второй проход, замер до добавления разреза по паузам; точность / найдено говорящих):

| Модель | clean | noisy_snr5 | quiet_dc |
|---|---|---|---|
| **CAM++ zh_en common advanced** (выбрана) | **99,0%** / 4 | 88,5% / 5 | **98,9%** / 4 |
| CAM++ zh-cn common | 99,0% / 4 | 88,5% / 5 | 98,9% / 4 |
| CAM++ en voxceleb | 72,4% / 6 | 70,1% / 3 | 53,9% / 4 |
| TitaNet small (прежний вариант) | 99,0% / 4 | 89,9% / 4 | 98,9% / 4 |

Порог кластеризации CAM++ 0,7: при 0,8 два голоса сливаются (89,7%). Без второго прохода точность любой модели 74–86%.

**Модель распознавания** (чистая запись, без предобработки):

| Модель | WER |
|---|---|
| **Parakeet TDT 0.6B v3** (выбрана) | **3,4%** (с предобработкой — 0,9%) |
| GigaAM v2 CTC | 12,1% |
| Qwen3-ASR 0.6B | 28,4% |

**Предобработка сигнала** (quiet_dc): без неё WER 4,3%, диаризация 94,1%, ошибка начала 937 мс; с ней — 2,6%, 99,0%, 25 мс.

**Шумоподавление GTCRN** (noisy_snr5): для всего конвейера WER вырос с 12,1% до 23,3%, только для диаризации точность упала с 89,9% до 85,0%. Не применяется.

## Проверка кода

- **Компиляция.** Kotlin-ядро скомпилировано против Android SDK 35, AAR sherpa-onnx 2.0.1 и исходников Kotlin API LiteRT-LM 0.19.1. Это аудио, движок, LLM, модели, очередь, сервисы, хранение и экспорт.
- **Юнит-тесты** (`./gradlew test`, 17 тестов) проходят. Покрыты ресемплер, предобработка, чистка и нарезка сегментов, разрез по паузам, уточнение спикеров (в том числе короткий кусок лишнего спикера), сигнатура колбэка диаризации для JNI, форматирование и проверка слов LLM на 20 общих примерах.
- **Разрез по паузам** в Kotlin и Python даёт одинаковые куски на всех трёх тестовых записях (сверено на выходе pyannote и VAD).
- **Python-реализация проверки слов** даёт те же ответы на тех же 20 примерах (`python tools/eval/llm_punctuation.py`).
- **Шаблон чата LLM** даёт одинаковый промпт, передаётся ли текст строкой (Python API) или списком частей (Kotlin API).
- **Не проверено в среде разработки:** экраны Compose, сборка APK и ответы LLM. Первые два проверяет сценарий `android.yml`, последнее — `eval.yml`.
